4. PicklistMapper

PicklistMapper est la seule portion de code écrite pour ce projet : une routine Java du référentiel Talend, partagée par les deux jobs. Elle traduit les valeurs de listes de sélection de l'org source vers l'org de destination.

4.1 Pourquoi une routine plutôt que des conditions dans les jobs

Une correspondance de valeurs peut s'écrire directement dans un tMap, sous forme de conditions imbriquées. L'approche tient jusqu'à quelques champs ; elle ne tient plus à l'échelle de ce projet, où une trentaine de champs de listes de sélection sont concernés, certains portant plus de cinquante valeurs distinctes.

Trois raisons ont motivé l'externalisation :

  • Volume. Des expressions conditionnelles de cette taille deviennent illisibles et impossibles à relire.
  • Maintenance. Corriger une correspondance ne doit pas obliger à ouvrir Talend. Toutes les règles vivent dans un fichier CSV externe : on l'édite, on relance, c'est tout.
  • Contrôle. Côté destination, la plupart des listes sont restreintes : une valeur absente du jeu de valeurs provoque un rejet. Il faut donc savoir, avant d'insérer, quelles valeurs sources n'ont pas de correspondance. C'est le rôle du fichier d'audit.

4.2 Ce que la routine ne fait pas

Deux choix d'architecture à connaître :

  • Elle ne crée jamais de valeur dans l'org de destination. Enrichir une liste de sélection est une opération de métadonnées, à faire par déploiement avant la migration. Le fichier d'audit sert précisément à identifier ce qu'il faut déployer.
  • Elle ne normalise ni la casse ni les accents. Contacte et Contacté sont deux valeurs distinctes. Chaque variante réellement présente dans les données doit avoir sa propre ligne dans le CSV. C'est volontaire : une normalisation automatique masquerait des incohérences de données qu'il vaut mieux voir.

4.3 Installation

  1. Référentiel Talend > Code > Routines > créer ou ouvrir PicklistMapper, coller le contenu de la classe (conserver la déclaration package routines;), enregistrer.
  2. Vérifier que la variable de contexte resource_dir pointe vers le répertoire contenant le fichier de correspondance.

4.4 Format du fichier CSV

Encodage UTF-8, séparateur ;, une ligne d'en-tête (ignorée).

object;source_field;source_value;target_value;target_field
Lead;Status;Disqualifié;Trash (Non-Converti)
Lead;Status;Marketing Automation;Lead
Account;Fonctions__c;Direction;DG
Account;Fonctions__c;XX_DEFAULT_XX;Autre
Lead;CauseNonQualifie__c;XX_DEFAULT_XX;
ColonneContenuRègles
objectNom d'API de l'objet sourceJamais le libellé.
source_fieldNom d'API du champ source Toujours le champ source, même quand la cible porte un autre nom — nécessaire pour les cas « une source, plusieurs cibles ».
source_valueValeur telle que stockée dans la source Sensible à la casse et aux accents. XX_DEFAULT_XX est réservé.
target_valueValeur écrite dans l'org de destination Vide = « vider le champ » (retourne null).
target_fieldNom d'API du champ cible, quand il diffère du champ source Optionnelle. Vide = la cible porte le même nom que la source.
Lecture par position, pas par en-tête. Ne jamais réordonner les quatre premières colonnes. Des colonnes libres (commentaires, volumétries…) peuvent être ajoutées après la cinquième ; elles sont ignorées.

Construire le CSV depuis les données, jamais depuis la liste de sélection

La bonne source est un dénombrement sur les données réelles :

SELECT champ, COUNT(Id) FROM objet GROUP BY champ

Les données contiennent presque toujours plus de valeurs que la liste active : valeurs historiques, libellés stockés comme valeurs après un renommage, variantes d'accentuation. Cas rencontré sur ce projet : un champ de statut avec 8 valeurs actives mais 28 valeurs distinctes réellement stockées.

Le fichier de correspondance fourni par le métier en début de projet s'est révélé incomplet sur ce point : il décrivait les listes, pas les données. Les correspondances ont été reconstruites à partir des dénombrements réels.

4.6 Ordre de résolution

Une ligne dont source_value vaut XX_DEFAULT_XX définit la valeur par défaut du champ : toute valeur source non listée reçoit cette cible.

  1. Correspondance exacte objet | champ | valeur — une cible vide est retournée comme null.
  2. Défaut du champ déclaré dans le CSV — le CSV prime toujours sur l'argument.
  3. Argument defaultValue de la méthode.
  4. null, et la valeur est enregistrée comme non mappée.

Les cas 2 et 3 sont enregistrés comme « defaut » dans l'audit : un défaut n'est jamais silencieux.

Collision. Si une valeur source vaut littéralement XX_DEFAULT_XX, un avertissement est émis une fois par champ et la valeur est traitée comme une valeur normale.

Stratégie sur les valeurs par défaut

Le défaut est un choix explicite par champ, pas un réflexe :

  • Champ porteur de sens métier (statut, raisons, fonctions…) → pas de ligne de défaut. Chaque valeur inconnue doit remonter dans l'audit et être tranchée.
  • Champ secondaire où « Autre » est une réponse honnête → ligne de défaut assumée, surveillée via l'audit.
  • Ne poser un défaut qu'après avoir fait le dénombrement du champ.
  • Sur un champ cible restreint, toute valeur produite — défaut compris — doit exister dans le jeu de valeurs, sinon rejet à l'insertion.

4.7 Les trois modes d'usage

Mode 1 — traduction simple

Le cas courant : une valeur source devient une valeur cible, sur un champ de même nom.

PicklistMapper.translate("Lead", "Status", row1.Status)

Mode 2 — valeur par défaut

Une ligne XX_DEFAULT_XX dans le CSV couvre les valeurs vides et les valeurs futures non encore listées.

Lead;Fonctions__c;XX_DEFAULT_XX;Autre

Mode 3 — cible multiple et cascades de listes dépendantes

Ces lignes ne décrivent pas une traduction de valeur. Elles expriment une règle structurelle de l'org de destination : la valeur qu'un champ parent doit porter pour qu'une valeur de champ enfant soit insérable. Le déclencheur est le même — une valeur source — d'où le fichier commun ; mais l'intention est différente. Ce n'est pas « X devient Y », c'est « quand la source vaut X, ce champ-là doit valoir Y pour que l'insertion passe ».

Cas 1 — cascade de listes dépendantes. Dans l'org de destination, Famille_de_produit__c contrôle Produit__c, qui contrôle Marche__c. Une valeur de marché n'est insérable que si les deux parents portent les bonnes valeurs — or ces champs parents n'existent pas côté source. Une seule valeur source doit donc alimenter trois champs cibles :

object;source_field;source_value;target_value;target_field
Opportunity;Marche__c;Interne;STIMI;
Opportunity;Marche__c;Interne;CCI;Produit__c
Opportunity;Marche__c;Interne;Gift Incentive;Famille_de_produit__c
// sortie Marche__c
PicklistMapper.translate("Opportunity","Marche__c",row1.Marche__c)
// sortie Produit__c
PicklistMapper.translateTo("Opportunity","Marche__c",row1.Marche__c,"Produit__c")
// sortie Famille_de_produit__c
PicklistMapper.translateTo("Opportunity","Marche__c",row1.Marche__c,"Famille_de_produit__c")

Une valeur source non listée retourne null sur les trois champs : aucune cascade partielle n'est posée, le trio reste cohérent.

Cas 2 — une source alimentant plusieurs cibles indépendantes. Même mécanisme, sans notion de dépendance. Exemple réel sur le Lead : le champ d'origine alimente trois champs de qualification distincts, une ligne de CSV par champ cible.

Limite connue. Les lignes d'une même cascade sont indépendantes dans le fichier : rien ne garantit qu'elles soient maintenues ensemble. Modifier la ligne enfant sans les lignes parentes produit un rejet Salesforce peu explicite (INVALID_OR_NULL_FOR_RESTRICTED_PICKLIST). Règle : toute modification d'une cascade se fait sur les trois lignes à la fois.

4.8 Le fichier d'audit

Écrit en fin de job par dumpUnmapped. Format :

object;field;source_value;type
TypeSignificationQue faire
unmapped Valeur rencontrée sans correspondance ni défaut. Résultat : null. Ajouter une ligne au CSV, décider un défaut, ou créer la valeur cible par déploiement de métadonnées.
defaut Valeur passée par un défaut. Surveiller : un volume anormal signale souvent une valeur mal orthographiée ou un cas métier oublié.

Les entrées sont dédoublonnées : le fichier liste des valeurs distinctes, pas un décompte de lignes traitées. Le résumé console de fin de job donne, par champ, le nombre de valeurs distinctes inconnues et passées par le défaut.

Ce fichier est un livrable de run, pas un artefact de mise au point : il fait partie des quatre contrôles décrits en page 8.

4.9 Branchement dans les jobs

tPreJob —OnComponentOk→ tJava :
    PicklistMapper.load(context.resource_dir + "/picklist_mapping.csv");
    // PicklistMapper.setDebug(true);   // test uniquement

tMap (expressions de sortie) :
    PicklistMapper.translate("Lead", "Status", row1.Status)

tPostJob → tJava :
    PicklistMapper.dumpUnmapped(context.resource_dir + "/picklist_unmapped.csv");

4.10 Pièges connus

PiègeConséquenceParade
État static partagé par JVM Avec des sous-jobs tRunJob dans la même JVM, un load() écrase ce qu'un autre a chargé. Sans objet ici (chaque job = une JVM). En cas d'orchestration par job parent : charger une seule fois au parent, ou utiliser loadMore.
Noms d'API, pas libellés Les correspondances ne matchent pas. SOQL lit et l'insertion écrit le nom d'API des valeurs.
Séparateur ; Une valeur contenant un point-virgule casserait l'analyse du fichier. Aucun cas rencontré à ce jour ; changer de séparateur si le cas se présente.
Encodage Un CSV enregistré en ANSI/latin-1 fait échouer silencieusement les correspondances sur les valeurs accentuées. UTF-8 obligatoire.
Réordonnancement des colonnes Lecture par position : tout décale. Ne jamais déplacer les quatre premières colonnes.
Mode debug laissé actif Une ligne de console par traduction : exécution ralentie, sortie illisible. Laisser setDebug commenté hors phase de test.
