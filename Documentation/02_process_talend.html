2. Process Talend

Les deux jobs sont construits sur le même schéma, répété autant de fois qu'il y a d'objets. Comprendre un sous-job, c'est les comprendre tous. Cette page décrit ce schéma, ce qu'il produit, et les trois mécanismes qui peuvent faire qu'un job se termine en vert alors que le résultat est incomplet.

2.2 La requête SOQL définit le périmètre réellement migré

C'est le point le plus important de cette page.

Le schéma du composant d'entrée contient tous les champs de l'objet Salesforce — 327 colonnes sur l'Opportunité, par exemple. Mais seuls les champs énumérés dans la clause SELECT sont réellement remplis à l'exécution.

Conséquence : un champ mappé dans le tMap mais absent du SELECT arrive vide dans l'org de destination, sans erreur, sans rejet, sans trace. Le compteur d'insertions réussies reste identique.

La clause WHERE joue le même rôle pour les enregistrements : elle est la définition opérationnelle du périmètre. Les requêtes complètes et leur lecture détaillée sont en page 3.

2.3 Les lookups inter-orgs

Un enregistrement source référence ses parents par des Id de l'org source, inutilisables dans l'org de destination. Chaque rattachement passe donc par un lookup : une requête sur l'org de destination qui ramène les couples Id / IdGlady__c, jointe dans le tMap.

Le type de jointure décide de ce qui arrive aux orphelins

TypeComportement si le parent n'est pas trouvé
Jointure externe (par défaut) L'enregistrement passe, le champ de rattachement reste vide.
Jointure interne L'enregistrement est écarté du flux. Il n'apparaît ni dans le fichier de résultat, ni dans le fichier de rejet : il disparaît.

Tous les lookups sont chargés en mémoire une fois pour toutes au démarrage du sous-job (Load once) et retiennent une correspondance unique par clé.

Deux lookups particuliers

  • Record type par DeveloperName. L'Id technique d'un record type diffère d'une org à l'autre ; son DeveloperName est stable. Les jobs résolvent donc l'Id à l'exécution à partir du nom. Les noms utilisés sont écrits en dur dans les requêtes : ils sont listés en page 3 et doivent être vérifiés dans chaque org cible.
  • Code NAF. Côté destination, le code NAF n'est pas un texte mais une relation vers un objet référentiel. Le code source est normalisé (point retiré, mise en majuscules) puis résolu vers l'Id de l'enregistrement du référentiel.

2.5 Gestion des erreurs

Aucun code spécifique : les jobs utilisent le chemin Reject standard du composant de sortie Salesforce. Chaque enregistrement refusé y arrive avec le motif du refus, ce qu'un simple compteur ne donnerait pas.

Tous les fichiers de rejet ont le même format :

id_source ; salesforce_id ; result ; errorCode ; errorFields ; errorMessage
ColonneContenu
id_sourceId de l'enregistrement dans l'org source — permet de le retrouver et de le corriger à la source
salesforce_idId de destination, vide sur un rejet
resultInserted ou failed
errorCodeCode Salesforce : FIELD_CUSTOM_VALIDATION_EXCEPTION, DUPLICATE_VALUE, STRING_TOO_LONG…
errorFieldsChamps en cause
errorMessageMessage d'erreur, souvent directement lisible par le métier

La présence de l'Id source rend ces fichiers directement exploitables comme support d'échange avec le métier pour le nettoyage des données. Voir page 8.

Trois familles :

  • ...Data.csv — ce qui est envoyé à l'org de destination, après mapping et traduction des listes de sélection. Le seul endroit où l'on voit les valeurs transformées telles qu'elles partent : précieux pour vérifier une correspondance ou une valeur vide inattendue.
  • ..._ok.csv — les insertions réussies (ou, dans le job Opportunités/Devis, les tables de correspondance d'Id : voir l'encadré ci-dessus).
  • ..._ko.csv — les rejets, avec leur motif.

2.7 tPreJob et tPostJob

Les deux jobs encadrent leur traitement par deux composants Java :

// tPrejob → tJava_1
PicklistMapper.load(context.resource_dir + "/picklist_mapping.csv");

// tPostjob → tJava_2
PicklistMapper.dumpUnmapped(context.resource_dir + "/picklist_unmapped.csv");

Le premier charge en mémoire le fichier de correspondance des valeurs de listes de sélection ; le second écrit, en fin de job, l'inventaire des valeurs rencontrées sans correspondance. Voir page 4.

Une ligne PicklistMapper.setDebug(true); est présente en commentaire dans le tPrejob. Elle trace en console chaque traduction : utile pour un test sur un petit volume, à laisser désactivée pour un run réel.

2.8 Variables de contexte

Un groupe de contexte partagé par les deux jobs porte deux variables :

VariableContenuUtilisée par

resource_dirRépertoire du fichier de correspondance des listes de sélection et du fichier d'audit Les composants tPrejob / tPostjob

Aucun chemin n'est écrit en dur dans les composants : changer de poste ou d'environnement se fait en modifiant ces deux valeurs. Le groupe de contexte accepte plusieurs jeux de valeurs (une colonne par environnement), sélectionnables au lancement.

2.10 Pourquoi un job « vert » peut être faux

Trois mécanismes produisent des données incomplètes sans lever la moindre erreur. Le compteur d'insertions réussies ne les voit pas, les fichiers de rejet non plus.

  1. Un champ mappé mais absent du SELECT arrive vide dans l'org de destination.
  2. Un lookup en jointure interne dont le parent manque fait disparaître l'enregistrement enfant du flux, sans ligne de rejet.
  3. Un champ sans droit d'écriture pour l'utilisateur d'intégration est ignoré silencieusement par Salesforce.

C'est pour cette raison que la vérification d'un run ne se limite jamais au compteur de succès. Les quatre contrôles à effectuer sont décrits en page 8.

2.11 Lire une exécution dans le Studio

Pendant et après l'exécution, Talend affiche en vert, sur chaque lien du schéma, le nombre de lignes qui l'ont traversé. C'est le moyen le plus rapide de localiser une anomalie :

  • Le compteur en sortie de la requête source donne le volume réellement extrait : s'il est nul ou très inférieur à l'attendu, le problème est dans la clause WHERE, pas dans le mapping.
  • Un écart entre l'entrée et la sortie d'un tMap signale une jointure interne qui écarte des lignes.
  • Un compteur à zéro sur un sous-job enfant alors que le parent a bien produit des enregistrements indique une table de correspondance vide ou un rattachement qui ne se fait pas.
