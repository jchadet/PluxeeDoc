5. Décisions & arbitrages — transverses

Cette page et les deux suivantes recensent les choix non triviaux de la migration. Elles répondent à la question « pourquoi est-ce fait comme ça ? » et, surtout, « qu'est-ce qu'il faut revoir avant la production ? ».

5.1 Comment lire ces pages

Chaque arbitrage suit la même grille :

ContexteLe problème rencontré.
DécisionCe qui a été fait, et où c'est implémenté.
LimiteCe que la décision coûte, en clair.
En productionCe qu'il faut reconsidérer.

Trois statuts qualifient le degré de certitude :

ValidéArbitré avec le métier ou imposé par la plateforme.
DéduitÉtabli par analyse des données réelles, sans validation formelle.
À confirmerHypothèse de travail, à faire trancher.

T1. Bypass des règles de validation et Permission Set de migration

Contexte. Les règles de validation de l'org de destination sont conçues pour la saisie manuelle. Appliquées à des données historiques qui n'y ont jamais été soumises, elles bloquent massivement l'import : environ 3 700 rejets sur les seuls leads en recette (date de première commande, format de téléphone, SIRET, type de société, longueur des noms). Côté opportunités, plusieurs règles exigent des champs qui n'ont aucune source — ils sont liés à une restructuration produit postérieure à l'org source : aucun mapping ne peut les remplir.

Décision (validée). Un Permission Set dédié, Data Migration Users, regroupe tous les contournements nécessaires et est assigné à l'utilisateur d'intégration :

ÉlémentRôle
Bypass_validation_rules__c (champ utilisateur)Neutralise les règles de validation personnalisées Lead et Opportunité.
Bypass duplicated rules (champ utilisateur)Neutralise les règles de doublons sur le Lead.
EditClosedOpportunity (permission personnalisée)Autorise la modification d'opportunités fermées.

Limite. Le bypass masque les problèmes plutôt qu'il ne les résout : les enregistrements s'insèrent, mais des champs restent vides ou mal formatés sans qu'aucune alerte ne le signale. Les fichiers de rejet ne remontent plus ces cas. Par ailleurs, le bypass ne couvre pas les contraintes de plateforme (date de conversion antérieure à la date de création, listes de sélection restreintes, dépassement de longueur) : celles-là exigent une correction dans le mapping ou dans les données source.

En production.

  • Assigner le Permission Set avant chaque run, le retirer après pour restaurer les contrôles de saisie.
  • Pour améliorer la qualité des données : désactiver le bypass, relancer, et traiter les rejets un par un — nettoyage à la source ou enrichissement du mapping.
  • Si de nouvelles règles bloquent l'import, compléter ce Permission Set plutôt que d'en créer un autre.
  • À compléter : la liste exhaustive des règles contournées et des champs laissés vides n'est pas constituée (page 9).

T2. Record types — un seul par objet, résolu par son nom

Contexte. L'Id technique d'un record type diffère d'une org à l'autre : il ne peut pas être repris tel quel. Sur les premières versions du job Lead, le record type n'était pas mappé du tout : les leads prenaient le record type par défaut de l'org de destination.

Décision (validée). Tous les objets résolvent leur record type par lookup sur le DeveloperName, clé stable entre orgs. Un seul record type est utilisé par objet ; les devis partent sur le record type standard. Les noms utilisés figurent en page 3.

Limite. Le nom est écrit en dur dans la requête. S'il n'existe pas dans l'org cible, le lookup ne remonte rien, la jointure étant externe le job continue, et le record type par défaut s'applique — sans erreur.

En production. Vérifier les trois DeveloperName dans le Setup de l'org cible avant tout run. Si le modèle de destination introduit plusieurs record types porteurs de logique métier (mises en page, listes restreintes par record type), le mapping devra être conditionné.

T3. La clé externe IdGlady__c

Contexte. Aucun rattachement inter-orgs n'est possible sans une clé commune.

Décision (validée). Chaque objet migré porte un champ IdGlady__c contenant l'Id 18 caractères de l'enregistrement source, déclaré en clé externe unique. Il sert à trois choses : rattacher les enfants à leurs parents, permettre le rejeu, et tracer l'origine de chaque enregistrement.

Côté source, ID_18__c est une formule CASESAFEID(Id) : requêtable, non insérable. Elle sert de clé de lecture, jamais de champ cible.

Limite. L'unicité de la clé est ce qui protège des doublons ; c'est aussi ce qui fait échouer le rejeu (voir T8). Sur le job Lead, le fichier de résultat a présenté une colonne d'Id source vide lors de certaines exécutions ; le contournement consiste à interroger directement l'org de destination :

SELECT Id, IdGlady__c FROM Lead WHERE IdGlady__c != null

En production. Vérifier que le champ est déployé et accessible en écriture pour l'utilisateur d'intégration sur chacun des objets migrés, avant le premier run. Un champ présent mais sans droit d'écriture casse toute la chaîne de rattachement en silence.

T4. Conservation des dates d'audit

Contexte. Une migration qui perd les dates de création d'origine rend l'historique commercial inexploitable : toutes les opportunités apparaîtraient créées le jour de la bascule.

Décision (validée). CreatedDate et LastModifiedDate sont mappés depuis la source sur les objets qui le permettent. Cela requiert la permission Set Audit Fields upon Record Creation activée dans l'org de destination.

Limite. Les autres champs d'audit — CreatedById, LastModifiedById, LastActivityDate, SystemModstamp — ne sont pas repris : ils sont en lecture seule ou pointent vers des utilisateurs qui n'existent pas dans l'org de destination.

En production. Vérifier que la permission est bien active avant le run : sans elle, les dates sont silencieusement remplacées par la date d'insertion.

T5. Propriétaire des enregistrements migrés

Contexte. Les propriétaires source sont des utilisateurs de l'org source ; leurs Id n'ont pas d'équivalent dans l'org de destination.

Décision (déduite). OwnerId n'est pas mappé : tous les enregistrements migrés appartiennent à l'utilisateur d'intégration qui exécute le job.

Limite. Le portefeuille commercial n'est pas reconstitué. Les règles de partage, les files d'attente et les rapports par propriétaire ne refléteront pas la réalité d'avant migration.

En production. Si la reprise des propriétaires est souhaitée, elle suppose une table de correspondance entre les utilisateurs des deux orgs — à construire avec le métier. Le champ pourrait alors être résolu par lookup, sur le même principe que les autres rattachements.

T6. Activités — périmètre et normalisation du sujet

Contexte. Les Tâches et Événements sont rattachés à leur parent par WhoId (Lead, Contact) ou WhatId (Opportunité, Implémentation…).

Décisions.

PointDécisionStatut
Périmètre Job Lead : activités de leads uniquement (WhoId). Job Oppo : activités d'opportunités et d'implémentations (WhatId).Validé
WhatId sur les activités de lead Toujours vide côté source → non mappé.Validé
Récurrences Exclues (IsRecurrence = false) : elles n'ont plus de sens hors du contexte utilisateur d'origine. Validé
Sujet des Événements Normalisé sur deux valeurs : le sujet source devient RDV physique s'il vaut exactement cela, RDV tél/visio dans tous les autres cas. À confirmer

Limite. La normalisation du sujet est une perte d'information réelle : le libellé d'origine de chaque événement est remplacé, et tout ce qui n'est pas un rendez-vous physique est étiqueté comme un rendez-vous à distance, y compris les événements qui ne sont pas des rendez-vous. Le champ Type, lui, est traduit normalement par le PicklistMapper.

En production. Faire confirmer par le métier que la réduction à deux valeurs correspond bien au besoin. Sinon, conserver le sujet source tel quel, ou établir une correspondance plus fine via le PicklistMapper.

Constat utile. Les leads porteurs d'activités sont massivement des leads travaillés manuellement, souvent sans adresse e-mail. Un filtre sur l'e-mail élimine donc une bonne partie de la population qui possède des tâches — à garder en tête lors de l'interprétation des volumes d'activités.

T7. Rejets de qualité de données

Contexte. Une partie des rejets ne relève pas du mapping mais de la donnée source : code APE absent, date de clôture manquante, e-mail ou téléphone invalide, doublons, dépassements de longueur.

Décision (validée). Ces rejets ne sont pas corrigés côté ETL. Un rapport de qualité est produit à destination du métier, à partir des fichiers _ko, pour un nettoyage à la source.

Limite. Tant que la source n'est pas nettoyée, ces enregistrements ne passeront pas — ou passeront avec des données incomplètes sous couvert du bypass.

En production. Prévoir un nettoyage des données source en amont, puis rafraîchir l'environnement de test avec les données nettoyées avant de rejouer. La typologie des rejets et leur répartition entre technique et métier sont détaillées en page 8.

T8. Insertion sans upsert — conséquences sur le rejeu

Contexte. La migration doit pouvoir être relancée : pour un rattrapage des données créées depuis le dernier run, ou après correction d'un mapping.

Décision (validée). Les neuf composants de sortie sont en INSERT, pas en UPSERT. Le principe retenu est : un enregistrement migré une fois n'est pas migré deux fois. L'unicité de IdGlady__c fait office de garde-fou.

Limite — à bien comprendre. Un second run sur le même périmètre ne produit pas un delta : il retente tous les enregistrements, et ceux déjà migrés repartent en DUPLICATE_VALUE dans les fichiers _ko. Le résultat est correct — aucun doublon n'est créé — mais les fichiers de rejet sont alors massivement peuplés d'erreurs attendues, ce qui rend la lecture des vrais rejets délicate.

En production. Deux options :

  • Conserver l'insertion et restreindre le périmètre du rattrapage par une clause de date dans la requête source (par exemple sur CreatedDate). Simple, sans modification structurelle.
  • Passer en upsert sur IdGlady__c comme colonne clé. Le rejeu devient idempotent et les mises à jour de mapping se propagent aux enregistrements déjà migrés. Modification simple — un paramètre par composant de sortie — mais qui change la sémantique du run : à décider explicitement.

Le jour de la bascule, un rattrapage sera nécessaire dans tous les cas : des enregistrements continueront d'être créés dans l'org source entre le dernier run complète et la mise en service. Voir page 8.
