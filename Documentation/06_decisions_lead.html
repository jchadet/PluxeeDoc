L1. Périmètre — leads non convertis uniquement

Contexte. Un lead converti côté source devient inaccessible : il passe en lecture seule et disparaît derrière le Compte, le Contact et l'Opportunité issus de la conversion.

Décision (validée). La requête source porte IsConverted = false. Les leads convertis ne sont pas migrés : leurs données sont accessibles via les trois objets issus de la conversion, qui sont eux migrés par ailleurs.

Limite. L'historique du lead lui-même — date de création, origine, parcours de qualification — n'est pas repris pour ces enregistrements.

En production. Décision maintenue. Le job supporterait leur reprise sans modification structurelle si le besoin apparaissait : il suffirait de retirer la condition. Elle est à reporter dans les deux sous-requêtes d'activités (page 3).

L2. La conversion est recréée côté destination

Point le moins intuitif de la migration, et celui qui explique la plupart des règles de validation rencontrées sur le Lead.

Contexte. Le périmètre exclut les leads convertis (L1). Mais dans l'org source, certains leads non convertis au sens de la plateforme portent un statut métier qui équivaut à une conversion (clôture converti, qualifié, BANT complété). Côté destination, ces leads doivent apparaître comme convertis pour que les rapports d'entonnoir soient justes.

Décision (déduite). Le tMap reconstitue la conversion à partir du statut source :

Champ de destinationAlimentation
IsConvertedtrue si le statut source vaut l'un des trois statuts équivalents à une conversion
ConvertedDateDate de conversion source, dans les mêmes conditions ; null sinon
ConvertedAccountIdLookup sur le compte migré, par IdGlady__c
ConvertedContactIdLookup sur le contact migré
ConvertedOpportunityIdLookup sur l'opportunité migrée

Conséquence directe. C'est cette reconstitution qui déclenche les règles de validation « requis pour convertir » de l'org de destination, et donc les arbitrages L5, L6 et L7 ci-dessous. Ces règles ne portent pas sur le fait que le lead ait été converti dans l'org source, mais sur le fait qu'il soit marqué comme converti dans l'org de destination.

Limite. Les trois lookups dépendent de la migration préalable des comptes, contacts et opportunités. Non résolus, ils laissent les champs vides sans empêcher l'insertion : le lead est marqué converti mais sans cible de conversion.

En production. Faire confirmer par le métier que les trois statuts retenus correspondent bien à une conversion. Contrôler après run le nombre de leads marqués convertis sans compte de conversion : un volume élevé signale un problème d'ordonnancement, pas de mapping.

L3. Code NAF — résolution vers un référentiel

Contexte. Côté source, le code d'activité est un champ texte au format pointé (10.92Z). Côté destination, c'est une relation vers un objet référentiel Code_NAF__c.

Décision (validée). Le code source est normalisé dans le tMap — point retiré, mise en majuscules — puis résolu par lookup vers l'Id de l'enregistrement du référentiel :

Code_APE__c == null ? null : Code_APE__c.replace(".", "").toUpperCase()

Limite. Taux de résolution de 100 % lorsque le code source existe. Les leads sans code d'activité restent sans code NAF ; une règle de validation de l'org de destination l'exige pour la conversion, ce qui produit des rejets sur les leads concernés.

En production. Le référentiel Code_NAF__c (738 enregistrements) doit être chargé dans l'org de destination avant la migration : c'est un prérequis bloquant du guide de reprise. Les leads sans code d'activité relèvent du nettoyage à la source (T7).

L4. Origine du lead — une source, trois cibles

Contexte. Le modèle de destination éclate l'information d'origine sur trois champs distincts, là où la source n'en porte qu'un.

Décision (déduite). Le champ d'origine source alimente trois champs cibles via translateTo, chacun avec ses propres lignes dans le fichier de correspondance :

Origine_du_lead__c   ← translateTo(…, "Origine_du_lead__c")
Precisionorigine__c  ← translateTo(…, "Precisionorigine__c")
Hubspot_LeadSource__c ← translateTo(…, "Hubspot_LeadSource__c")

C'est le cas d'usage n°2 du PicklistMapper (page 4) : une source, plusieurs cibles indépendantes. Le champ standard LeadSource est par ailleurs traduit séparément.

Limite. Les trois lignes d'une même valeur source sont indépendantes dans le fichier : en modifier une sans les autres produit une origine incohérente entre les trois champs.

En production. Si le métier révise la correspondance des origines, la répercuter sur les trois champs simultanément — et sur le champ équivalent de l'Opportunité (page 7, arbitrage O4), qui réutilise la même logique.

L5. Fonction — valeur par défaut « Autre »

Contexte. Une règle de validation de l'org de destination exige un champ Fonction non vide pour les leads marqués convertis (voir L2). Le champ source correspondant porte 9 valeurs ; la cible est un jeu de valeurs global d'une cinquantaine de valeurs, auquel 17 valeurs ont été ajoutées pour couvrir la correspondance demandée par le métier.

Décision (à confirmer). Une ligne XX_DEFAULT_XX → Autre dans le fichier de correspondance. Tout lead dont la fonction source est vide ou non mappée reçoit « Autre ».

Limite. Le défaut s'applique à tous les leads, pas seulement à ceux marqués convertis : c'est une pollution mineure, assumée pour la simplicité du mapping.

En production. Le bypass des règles de validation (T1) serait plus propre que le défaut sur les leads non convertis : il éviterait de renseigner une fonction fictive sur des enregistrements où elle n'est pas exigée. Les 17 valeurs ajoutées au jeu de valeurs global doivent être déployées dans l'org cible avant le run.

L6. Type de société — valeur constante

Contexte. Une règle de validation exige un type de société non vide pour les leads marqués convertis. Aucun champ équivalent n'existe côté source.

Décision (à confirmer). La valeur Entreprise est écrite en dur dans le tMap, conditionnée aux mêmes statuts que la conversion (L2). Les autres leads restent avec le champ vide.

Limite. Donnée approximative. Les leads relevant d'un comité social et économique devraient logiquement porter une autre valeur, mais aucun moyen fiable de les distinguer n'existe côté source dans le périmètre actuel.

En production. Le bypass reste la meilleure solution pour ne pas polluer ce champ avec une valeur non vérifiée. Si le métier fournit une règle de distinction — record type, segment, marché… — le mapping peut être conditionné sans difficulté.

L7. Raison du statut — défaut conditionné

Contexte. Une règle de validation exige une raison non vide pour les leads dont le statut de destination correspond à une non-conversion (mise au rebut, remarketing). Le champ source équivalent est souvent vide, même pour des leads non qualifiés.

Décision (à confirmer). La logique est entièrement dans le tMap, pas dans le fichier CSV : la traduction n'est appliquée que si la raison source est renseignée, ou si le statut traduit correspond à l'un des deux statuts de non-conversion. Les autres leads gardent le champ vide.

Limite. La raison réelle de non-conversion n'est pas connue pour ces leads : la valeur posée est une approximation.

En production. Si le métier fournit une règle plus fine, la condition du tMap peut être ajustée. Noter que cette logique étant dans le job et non dans le CSV, sa modification demande d'ouvrir Talend.

L8. Tranche d'effectif — correspondance approximative

Contexte. Deux découpages d'effectif qui ne coïncident pas. Le champ numérique standard NumberOfEmployees a d'abord été envisagé comme source, avec un découpage par formule ; il a été abandonné au profit de la liste de sélection source dédiée, mieux renseignée.

Décision (déduite). Correspondance « tranche englobante » via le PicklistMapper :

Limite. Les correspondances marquées « à cheval » sont imprécises : une tranche source chevauche deux tranches de destination, et une seule est retenue. La création de tranches alignées côté destination a été volontairement écartée : les bornes source ne correspondent à aucun découpage propre, l'ambiguïté serait simplement déplacée.

En production. C'est au métier de définir les valeurs cibles s'il souhaite un découpage exact. En l'état, correspondance dégradée assumée.

Le cas de la date de clôture estimée

Une date de clôture estimée future n'a aucun sens pour un lead historique : la règle n'a pas été conçue pour de la reprise de données. Le champ est donc laissé vide ; la règle ne se déclenche pas sur un champ vide.

À savoir : cette règle de validation ne comporte pas de test sur le champ de bypass utilisateur. Si le champ devait un jour être alimenté avec des dates passées, il faudrait au préalable modifier la règle pour y intégrer le bypass.

Activités des leads

Les Tâches et Événements rattachés aux leads suivent les décisions transverses T6 de la page 5 : périmètre hérité de celui des leads, récurrences exclues, champ de rattachement secondaire non mappé, et normalisation du sujet des événements sur deux valeurs — le point à faire confirmer par le métier.

Les champs de statut et de priorité des tâches, ainsi que le type des événements, sont traduits par le PicklistMapper.
